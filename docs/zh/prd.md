> 完整版｜版本 1.1｜2026-11-01  
> 适用范围：网易云音乐手机端  
> 文档状态：需求评审稿；实施效果待验证  
> 页面说明：需求一复用现有界面；需求二、三包含拟议交互原型

## 一、文档摘要

需求覆盖作品关联补全、听歌流程推广控制和举报反馈。推广控制结合任务场景与用户匹配，并保障个性化布局中的功能入口可达。作品关联补全复用现有界面。

| 需求 | 用户要完成的任务 | 已确认的现有措施 | 需要解决的缺口 | 优先级 |
|---|---|---|---|---|
| 需求一：歌手作品完整浏览 | 从艺人主页找到其明确参与、且平台已经收录的作品 | 热门歌曲、查看全部歌曲、专辑页及时间排序已存在 | 多人合集的歌曲署名与专辑、艺人主页关联不完整，造成作品遗漏 | P1；配套改进建议 |
| 需求二：听歌流程推广干扰控制 | 打开应用后找歌、识曲、播放及恢复原任务 | 平台已有会员减免、部分页面关闭和推广关闭能力 | 当前任务中的推广干扰、内容匹配及反馈，以及差异化首屏的功能可达性 | P1；现网复测后进入开发 |
| 需求三：评论及陌生互动举报反馈 | 提交后持续查询进度，结案时了解结果及后续选择 | 已有举报入口与系统通知回执，部分公开案件有最终反馈 | 已提交回执之后的进度可见性、结案反馈覆盖与记录可找回 | P0 |

P0 表示涉及用户安全与信任，应优先保证完整处理流程；P1 表示核心体验改进，可按照研发资源安排实施。

## 二、背景与证据

### 2.1 研究材料

需求判断采用三类材料：

1. 具有时间、入口、操作过程和后果的公开用户反馈，用于确定问题场景。
2. 界面截图、操作记录及公开版本信息，用于核对具体场景和现有能力。
3. 问卷数据，用于辅助理解问题可能影响的使用范围。

公开反馈属于定性材料，只能证明相应问题曾在具体场景中出现。问卷样本集中于年轻学生群体，数据不代表网易云音乐全部用户。

### 2.2 需求一的证据

案例环境：网易云音乐 iOS 版 9.6.15。日文版《メメントモリ Lament Collection Vol.4》的歌曲署名关联 Bank of Innovation, Inc.（BOI），专辑署名为 Various Artists；从 BOI 主页的专辑列表浏览时能找到英文版，日文版需要另行搜索。

网易云公开检索返回日文版专辑 ID 404473299，署名 Various Artists，发行公司 Bank of Innovation, Inc.；BOI 艺人 ID 59602882 的专辑列表返回 10 张专辑，包含英文版 ID 403874212，未包含该日文版。

BOI 官方公告确认日文版、英文版均于 2026-10-21 发布，各收录 42 首。TuneCore 在 BOI 的“参加作品”中展示日文版合集，同时保留 Various Artists 的专辑署名。

来源：[日文版专辑](https://music.163.com/album?id=404473299)、[BOI 主页](https://music.163.com/artist?id=59602882)、[官方发行公告](https://boi.jp/news/261021o.html)、[发行平台艺人页](https://www.tunecore.co.jp/artists/bankofInnovation)。

### 2.3 需求二的证据

2026-11-01 的界面与操作记录覆盖进入应用、浏览推荐、播放、阅读评论及返回前台：播放器出现领时长推广，音频继续播放，音乐展示区域被大卡片占用；返回前台出现带“点击或扭动手机”提示的全屏广告；评论区同时存在功能活动内容和赞赏引导；免费听歌时长结束前出现续时长提示；刷新或浏览动作达到一定幅度时展开顶部活动。

不同账号的启动首屏分别呈现心动页和推荐页。心动页保留右上角搜索图标及底部搜索入口，记录中的困难涉及入口辨认、识曲发现和首页模式切换。该案例用于检验差异化布局对功能可发现性、任务完成和内容推荐效果的共同影响。账号间首屏差异的成因需要版本、设置及实验信息核对。音乐内容推荐与商业广告分别记录，二者均适用关键入口保护规则。

第9题中51/110人选择“广告、弹窗或活动提示影响使用”，占46.4%；第8题广告干扰控制均分为2.50/5。2025年App Store反馈及2024年广告操作投诉还涉及后台返回推广、会员提示、关闭及误跳转。历史反馈与界面记录用于确定场景，发生频率和不同账号的差异通过正式版本复测记录。

来源：2026-11-01界面与操作记录；[App Store用户反馈](https://apps.apple.com/cn/app/id590338362?platform=ipad&see-all=reviews)；[广告操作投诉](https://tousu.sina.com.cn/complaint/view/17377128251)。

### 2.4 需求三的证据

2026-11-01的使用反馈记录中，举报提交后可在应用内系统通知看到“已提交”，后续处理进度和结案结果在该路径中不可见。用户难以区分等待处理、材料不足、未认定违规及通知遗漏等情况。

2025年App Store反馈涉及“一起听”中的骚扰及举报等待；2026年评论举报投诉涉及集中攻击和处理结果不确定，后续补充记录了最终反馈。现有入口和部分结果反馈可以复用，需求重点为受理之后的持续查询、各类结案说明与通知关联。

公开反馈同时包含对评论故事和社区氛围的正面评价。违规处置、个人屏蔽及内容偏好分别处理，保护正常表达与用户自主选择。

来源：2026-11-01举报使用反馈记录；[App Store用户反馈](https://apps.apple.com/cn/app/id590338362?platform=ipad&see-all=reviews)；[评论举报投诉](https://tousu.sina.com.cn/complaint/view/17394848186)。

## 三、产品目标与范围

### 3.1 产品目标

| 需求 | 产品目标 | 用户获得的结果 |
|---|---|---|
| 需求一 | 补齐有明确署名依据的作品关联 | 从艺人主页找到相关合集，了解参与身份，并区分语言版本 |
| 需求二 | 按当前任务控制推广，并根据权益、兴趣及反馈匹配内容，保障功能入口可达 | 顺利找歌、识曲和听歌，自主选择推广及常用路径 |
| 需求三 | 提供持续可查的处理状态和覆盖全部结案类型的反馈 | 知道是否受理、是否需要补充、处理结论及下一步操作 |

需求一通过关联样本核对和指定专辑查找验收。需求二、三根据业务周期和有效事件量确定基线观察期，由产品、运营和研发依据基线确定目标值。

### 3.2 范围

| 需求 | 本期包含 | 本期排除 |
|---|---|---|
| 需求一 | 署名核对、歌曲与专辑关联、现有列表展示、语言版本说明、关联纠错 | 版权采购、未收录作品补录、独立作品中心、新增批量整理功能 |
| 需求二 | 场景与形式控制、跨页面频控、推广匹配与反馈、权益提示、核心入口保护、用户显示偏好 | 广告定价、会员价格、歌曲授权变更、全量推荐算法重建 |
| 需求三 | 举报受理、进度查询、材料补充、结案反馈、通知关联、延迟说明，以及退出和屏蔽 | 完整社区处罚制度、执法处置、创作者直接删除所有公开评论、公开被举报人隐私 |

### 3.3 非目标

- 需求一不改变歌曲授权和可播放状态。
- 需求二保留合理的商业展示空间，安全通知、账号风险提示和服务中断通知不受普通推广频次限制。
- 需求三不保证每次举报都会产生处罚；审核结论取决于内容、证据和社区规则。
- 本期不处理音乐云盘歌曲加入歌单、个人音乐跨端冲突和版权替代版本。

## 四、目标用户与核心场景

### 4.1 用户类型

| 用户类型 | 主要行为 | 对应需求 |
|---|---|---|
| 目标明确的找歌用户 | 从搜索、歌曲页进入歌手主页，查找完整作品 | 需求一 |
| 合作作品及游戏音乐听众 | 沿艺人或制作主体主页查找多人合集及语言版本 | 需求一 |
| 有即时任务的用户 | 打开应用后搜索、识曲或进入个人音乐 | 需求二 |
| 浏览推荐的用户 | 探索音乐与活动，并调整内容偏好 | 需求二 |
| 免费用户 | 打开应用、返回应用、切歌时可能接触推广 | 需求二 |
| VIP 或 SVIP 用户 | 关注会员减免是否生效，希望控制非核心模块 | 需求二 |
| 评论区参与者 | 阅读评论、举报违规内容、反馈无关内容 | 需求三 |
| 陌生互动参与者 | 使用“一起听”等功能，可能需要退出、屏蔽和举报 | 需求三 |
| 音乐创作者 | 关注自己作品下的攻击性评论及举报进度 | 需求三 |

### 4.2 核心场景

#### 场景一：从艺人主页找到参与合集

用户进入 BOI 主页查找《MementoMori》系列音乐。在现有专辑列表中，能够找到已确认参与的日文合集，并进入原专辑页查看歌曲和署名。专辑保留 Various Artists 等真实发行署名。

#### 场景二：辨认同系列语言版本

用户查找同一合集的日文或英文演唱版本。已有专辑信息及列表卡片显示经确认的语言信息，分别打开对应专辑；相同标题不作为合并或覆盖的依据。

#### 场景三：启动与返回时接续任务

用户打开应用后搜索歌曲、识别现场音乐或进入个人歌单。不同首页模式均保留位置稳定、首屏可见且含义清楚的搜索、识曲和个人音乐入口。返回播放器时恢复原歌曲、队列及阅读位置，推广不覆盖当前任务。

#### 场景四：浏览推荐与调整偏好

用户主动浏览音乐或活动推荐。系统在符合当前任务及权益规则的展示机会中，依据已有兴趣和明确反馈匹配内容。用户可反馈不感兴趣、减少同类推广，并自行调整首页落点与可选内容顺序；推荐权重变化保持一级导航及关键功能入口稳定。

#### 场景五：查询举报进度与结论

用户举报评论后，在系统通知中收到受理回执，可直接打开同一条举报详情，并从举报记录重新找到。处理中、待补充及已结案有明确状态；未认定违规、材料不足等结论同样提供原因类别和适用的后续操作。

#### 场景六：退出互动并继续跟进

用户在陌生互动中需要停止接触，立即退出并按意愿屏蔽，再选择是否举报。退出不以完成表单为条件；已提交记录在离开互动后仍可查询。网络异常时保留草稿和本机隔离状态，联网后显示受理与屏蔽同步结果。

## 六、详细功能说明

### 6.1 需求一：歌手作品完整浏览

#### 6.1.1 署名与关联规则

- 按实际角色分别维护专辑艺人、歌曲演唱及其他参与者、制作主体和发行公司；Various Artists 可保留为多人合集的专辑署名。
- 根据发行方明确提供或内容运营复核确认的参与关系，将合集关联到对应艺人主页。发行公司名称、同名匹配和用户提交的线索须经关系核实后使用。
- 仅参与部分曲目的艺人，展示其参与身份及相关歌曲，避免把整张合集标为该艺人的个人专辑。

#### 6.1.2 补全流程

确认参与署名 → 关联歌曲与专辑 → 更新艺人作品列表 → 核对语言版本与重复项 → 从艺人页进入专辑验收。

入库时比对已确认的歌曲参与艺人和艺人专辑列表，对缺少对应合集的记录生成关联差异项。艺人身份、角色和参与范围一致的记录自动补齐；存在冲突的记录转内容运营复核。修正后刷新相关列表，并保留依据和变更记录。

#### 6.1.3 现有界面展示

复用艺人主页专辑列表、专辑信息区和歌曲署名入口。相关合集显示合辑属性与参与说明；语言依据发行信息标注。沿用现有排序、播放和收藏操作。

同一专辑在列表中按专辑 ID 去重；日文版、英文版及其他独立发行版本分别保留。关联作品的可见性、播放及收藏继续遵守现有权限。

#### 6.1.4 纠错与复核

用户通过现有专辑或歌曲信息纠错入口提交漏关联、错关联或版本信息问题。系统携带专辑、歌曲和艺人标识；内容运营核对来源后修正关系，同步刷新相关列表。证据不足时保留原信息与待核对记录。

### 6.2 需求二：听歌流程推广干扰控制

#### 6.2.1 设计原则与内容分类

推广按当前任务安排位置、时机和形式，并在允许展示的范围内匹配用户权益、兴趣及反馈。个性化可调整内容顺序、推荐权重和展示面积；一级导航及关键功能入口的位置、名称、可识别性和可用性保持稳定。可选模块的隐藏和常用路径变更由用户主动选择。

| 类型 | 典型内容 | 展示要求 |
|---|---|---|
| 商业广告 | 开屏、返回前台、页面内品牌广告 | 遵守权益、场景、总量及关闭规则 |
| 会员与活动推广 | 开通、续费、红包、演出及优惠活动 | 校验适用权益，按任务和兴趣匹配 |
| 功能引导 | 赞赏升级、语音评论介绍 | 入口附近轻提示，用户主动使用时展开说明；自动展开的阻断式引导计入打断总量 |
| 激励入口推广 | 看广告领时长的卡片或弹层 | 被动出现时计入推广频次 |
| 主动激励广告 | 用户明确选择后观看广告换权益 | 事先说明完成条件、所得权益及外部跳转，结束后恢复原任务 |
| 权益状态提示 | 受限歌曲、免费听歌时长到期 | 提供必要状态和选择，同轮操作合并提示 |
| 服务与安全通知 | 服务异常、账号风险等 | 按必要性送达，使用独立通知规则 |

#### 6.2.2 展示判断

1. 根据当前页面、正在输入、识曲采集、播放控件操作及用户主动点击等状态确定保护范围。搜索、识曲、切歌、支付、举报及恢复播放器期间，普通推广不覆盖入口、信息或操作区域。意图尚不明确时保留通用入口和选择，历史兴趣不作为改变操作路径的唯一依据。
2. 校验会员权益、素材关闭入口和跳转地址，不符合要求的推广停止展示。
3. 检查活动关闭记录、跨页面累计曝光、各形式上限及总体打断预算，命中限制时停止被动展示。
4. 在符合条件的候选中，按权益适用性、当前主动行为、明确兴趣及近期反馈匹配排序。
5. 选择适合当前位置的展示形式。转换为卡片时重新校验全部规则；无合适展示机会则放弃该次展示。
6. 素材实际显示并进入可视区域后记录曝光，请求和预加载不计入曝光。

#### 6.2.3 跨页面频次与关闭记录

- 进入前台开始使用会话，后台间隔达到服务端配置阈值后结束；切换页面不重置会话。
- 同一活动被主动关闭后，本次会话在各页面停止被动展示；用户主动进入活动详情不受该限制。
- 自动出现且要求用户关闭、确认、等待或退出才能继续当前任务的推广计入打断次数。商业广告、会员促销、活动和功能引导共用打断总量；固定信息流卡片单独控制曝光、位置和密度。各形式均遵守同活动关闭记录。
- 失去合适时机的推广取消本次展示，返回播放器时不集中补弹。
- 页面内卡片按位置和密度配置，不在阅读或控件操作时动态插入。
- 平台投放内容适用上述规则；用户发布的违规广告引流通过内容反馈和举报处理。

#### 6.2.4 音乐信息与任务接续

- 普通被动推广不覆盖或替换歌曲名称、演唱者、进度、播放控制及当前正在查看的封面或歌词。
- 歌曲正常播放且无关键操作时，推广可使用音乐信息与控制区之外的固定卡片位，并遵守曝光、密度和频次限制。
- 阅读评论时保留当前内容和位置；功能引导采用入口附近的轻提示，用户主动操作后再展开说明。
- 从评论、音效等页面返回播放器或从后台返回时，优先恢复原任务，普通推广不抢占恢复过程。
- 用户明确打开推广后进入相应详情或激励任务；完成或主动返回时接续原歌曲、队列和页面位置。恢复播放前校验当前权益，播放或暂停状态以用户最新选择为准。
- 音频连续性、音乐信息可见性和操作可用性分别验收。

#### 6.2.5 明确操作与防误触

- 普通活动弹层和页面内推广显示后提供可用关闭入口；关闭热区与落地页跳转热区分离。
- 刷新和内容浏览手势保持原功能；广告展开或跳转使用可见的独立操作入口。
- 通用广告落地页由明确点击触发，正常持握及摇动手机不自动跳转。
- 外部页面返回后恢复原状态，不重新触发同一推广；缺少关闭配置或地址校验失败的素材不展示。

#### 6.2.6 权益提示与主动激励

- 会员歌曲权限提示说明当前曲目的限制和可用选择。同一队列播放过程、同类限制及同一权益状态下合并重复提示，保留当前限制说明；权益变化或用户主动查询时更新信息，用户选择后进入相应可用路径。
- 免费听歌时长在现有入口持续显示，到期前以低干扰方式提醒；到期后明确继续听歌的可用方式。必要状态提示与可选会员促销分别处理。
- 领取时长前说明广告完成条件、所得时长、是否需打开外部应用及到账结果。用户明确选择后进入激励广告，结束后反馈权益并接续原任务。
- 已享有对应权益的用户，排除不适用的开通促销；续费内容按实际到期状态和用户选择展示。

#### 6.2.7 现状核验

| 维度 | 核验范围 |
|---|---|
| 账号 | 未登录、普通用户、免费听歌模式、有效会员、临近到期会员 |
| 首页 | 心动、推荐及其他启动落点，账号切换与偏好恢复 |
| 任务 | 搜索、识曲、个人音乐、开始播放、切歌、阅读评论、返回播放器及前台 |
| 网络 | Wi-Fi、移动网络、弱网和离线恢复 |
| 记录 | 推广类型与触发时机、信息遮挡、误跳转、重复展示、入口发现和任务完成 |

开发范围以当前正式版本确认的问题为准。

#### 6.2.8 用户与内容匹配

- 首期利用已有权益、关注收藏、近期主动行为及明确反馈进行规则匹配。当前任务和明确拒绝优先于长期兴趣判断。
- 兴趣定向遵守用户的个性化推广选择；停用时使用符合场景及权益规则的通用内容，功能入口和必要权益说明保持可用。
- 对权益不适用的候选，以及在反馈生效范围内已关闭或不感兴趣的活动先做排除，再对其余内容排序；减少同类推广按类别降低排序与频次。兴趣匹配不豁免场景、频次和入口保护规则。
- 兴趣信息不足时采用受控的通用展示位，并收集主动反馈。某次偶然收听不作为长期固定偏好的唯一依据。
- 内容匹配分别评估音乐推荐与商业推广；高点击率与任务完成、误触及负面反馈共同判断。

#### 6.2.9 个性化布局与入口保障

- 首页模式可突出不同内容，一级导航、搜索、识曲及个人音乐入口在各模式中保持位置稳定、首屏可发现、含义清楚和正常触控尺寸。
- 推荐权重变化不自动折叠关键入口、缩小热区、降低视觉辨识度或增加其操作层级。其他功能保留清晰稳定的到达路径。
- 首页落点和可选模块显示由用户选择，偏好按账号保存；系统推荐变化不覆盖用户设置。
- 验收同时检查入口是否存在、能否被及时发现及任务是否完成，覆盖首次使用与账号切换场景。

#### 6.2.10 反馈与偏好生效

| 操作 | 生效范围 | 持续与恢复 |
|---|---|---|
| 关闭 | 当前会话内同一活动的全部素材停止被动展示 | 新会话重新校验权益、频次及其他偏好 |
| 不感兴趣（此活动） | 同一活动跨页面、跨会话停止被动展示 | 持续至活动结束或用户主动恢复 |
| 减少此类推广 | 降低该类别的排序和频次上限 | 按账号保存，用户可调整或恢复；不关闭对应功能入口 |

同活动更换素材或广告位不重置反馈。匿名状态的关闭记录按当前设备会话保存，登录后采用对应账号偏好；账号切换不沿用另一账号的私人偏好。反馈入口说明作用范围，网络异常时保留本次操作并在同步完成后更新状态。

### 6.3 需求三：评论及陌生互动举报反馈

举报受理后提供持续可查的状态记录，结案时告知结论、原因类别与后续操作。退出、屏蔽和材料保留为配套能力。

#### 6.3.1 场景化入口

- 复用评论、私信及“一起听”等场景的举报、屏蔽和内容反馈入口。
- 提交时带入内容标识、相关账号、场景及必要上下文。退出互动后仍可从举报记录找到已受理事项。
- 复用现有消息详情与帮助反馈区域承载举报记录，系统通知和记录列表进入同一详情。

#### 6.3.2 问题分类

| 情况 | 处理入口 | 用户可获得的结果 |
|---|---|---|
| 疑似辱骂、威胁、骚扰或欺诈 | 举报 | 审核结论及原因类别 |
| 单纯无关、重复或低质量内容 | 内容反馈 | 调整个人展示或提交质量线索 |
| 个人不喜欢的正常表达 | 不感兴趣 | 管理个人内容偏好 |
| 不希望继续接触某账号 | 退出或屏蔽 | 停止对应范围的互动 |

用户可提交疑似违规线索，最终认定由审核完成。个人屏蔽和内容偏好不代表平台认定违规。

#### 6.3.3 材料提交与受理

- 评论举报携带被举报内容和必要上下文；陌生互动携带会话标识及用户选择的相关记录。语音材料限于已明确告知且按规则留存的内容。
- 请求发出时显示提交中；服务端确认并返回记录编号后显示已受理。网络失败保留草稿，超时先核对受理结果，避免重复创建。
- 同一请求重试复用提交标识。已受理后再次提交相同事项，指向原记录并允许补充新线索。

#### 6.3.4 状态模型

| 状态 | 判定条件 | 页面信息 |
|---|---|---|
| 草稿 | 尚未提交或确认提交失败 | 编辑、删除、重试 |
| 提交中 | 请求已发出，受理结果未确认 | 正在确认提交结果 |
| 已受理 | 服务端建立记录，等待开始处理，包含排队 | 编号、受理时间、详情入口 |
| 处理中 | 规则或人工处理任务实际开始 | 当前状态及最近实际更新时间 |
| 待补充 | 明确需要用户提供必要信息 | 缺少的材料、补充入口及截止条件 |
| 已结案 | 形成处理结论并保存可查询结果 | 结论、原因类别、结案时间、后续操作 |

状态和更新时间对应真实受理、处理开始或材料变更事件。排队期间显示已受理，处理实际开始后更新为处理中；无实际进展时不伪造进度比例或人工处理文案。补充完成返回处理流程，超过补充期限按规则给出明确结论。

#### 6.3.5 结案反馈

| 结论 | 必须说明的信息 | 适用的后续操作 |
|---|---|---|
| 认定违规并采取措施 | 可公开的处理类别及完成情况 | 查看结果、管理个人屏蔽 |
| 未认定违规 | 本次未采取违规处置及原因类别 | 查看说明、补充新线索或按规则申请复核 |
| 材料不足、无法核实 | 未能核实的原因及材料要求 | 在允许范围补充材料或重新反馈 |
| 超出受理范围 | 关闭原因及适用渠道 | 前往对应渠道 |
| 重复事项已关联 | 原记录入口及当前状态 | 继续跟进原记录和结果 |
| 用户撤回 | 撤回时间及记录状态 | 查看记录；必要安全处理按独立规则执行 |

- 每件已受理举报结案时均保存结论、原因类别、时间及后续操作，包括未认定违规和未采取措施的情况。
- 结果与结案状态共同保持可查询。结果写入异常时重试并告警，避免只显示已结束而没有结论。
- 反馈不披露举报人身份、审核人员、关联案件细节及内部风控信号。个人屏蔽状态与平台处理结论分别显示。

#### 6.3.6 退出与屏蔽

- 用户可立即退出当前互动，再自主决定是否屏蔽或举报。退出不等待举报提交或审核结果。
- 网络异常时先停止本机互动并隐藏对方，服务端未确认时显示同步状态；确认后更新对应范围的屏蔽结果。
- 操作前说明对评论、私信及陌生互动的适用范围，用户可在现有设置中调整。

#### 6.3.7 重复事项与复核

- 重复提交关联原记录；多名用户的线索可由后台合并审核，各自的受理和结果记录独立可查。
- 结案后补充新材料或申请复核，按规则关联原记录并保留历史结论，避免覆盖前次结果。
- 举报数量用于线索聚合和风险排序，处置依据内容、证据及社区规则；正常表达保留相应复核渠道。

#### 6.3.8 通知与记录一致性

- 受理、待补充、首次超时及结案等关键节点生成应用内系统通知，点击后进入对应举报详情。普通中间流转更新详情，避免逐状态重复推送。
- 设备推送按用户设置发送；关闭推送、发送失败或漏看消息，不影响举报记录及应用内结论查询。
- 通知保存发送时的记录编号、状态及结论版本，点击后进入同一详情，显示当前状态和原节点历史；结论更正保留前次结果并生成更正通知。通知失败独立重试，不回退案件状态。

#### 6.3.9 等待与延迟说明

- 服务时限按风险和事项类型配置。超过时限仍未结案时，生成延迟说明并进入内部升级处理，结案后继续反馈结果。
- 待补充期间明确等待用户操作；总等待时间与平台处理耗时分别记录。
- 最近更新时间仅随实际状态或处理事件变化。预计时间仅在具备可靠依据时提供。

### 8.1 需求一主流程

内容处理：核对署名与角色 → 建立参与关系 → 更新艺人专辑索引 → 去重及版本核对 → 发布关联。

## 九、页面原型与状态说明

以下原型用于表达内容层级和交互状态。视觉稿阶段沿用网易云音乐红、黑、白的基础视觉语言，并遵循现有组件规范。

### 9.1 需求一：现有页面复用

需求一按信息与关联补全交付，复用现有艺人主页、专辑列表、专辑信息和纠错入口。现有热门歌曲、查看全部及时间排序继续使用。

### 9.2 需求一：显示与状态要求

- 合集保留真实专辑署名，同时展示已确认的艺人参与关系。
- 同系列不同语言版本分别显示，信息不明时保留原发行信息，等待核对。
- 仅参与部分歌曲时，参与说明与实际曲目一致。
- 纠错完成后，相关页面展示一致；误关联支持撤销并刷新列表。

### 9.3 原型三：播放页推广展示与关闭

- 播放期间不插入推广语音；权益、频次或素材校验未通过的推广不显示。

## 十、业务规则与异常处理

### 10.1 共通规则

- 页面必须为失败、空状态和退出提供明确出口。
- 用户的播放、推广关闭和举报草稿均需与当前账号及会话正确关联。
- 作品关联更新及其他重复提交使用幂等校验，避免重复展示、重复记录推广点击或重复创建案件。
- 文字、图标和颜色共同表达关键状态，不能只依赖红绿颜色。
- 所有方案原型中的文案由内容、商业化、安全和法务在上线前复核。

### 10.2 需求一异常规则

| 异常 | 处理 |
|---|---|
| 参与者同名或角色冲突 | 保留原信息，转运营复核后更新 |
| 歌曲及专辑关系不一致 | 对照发行资料核对参与范围 |
| 同一合集重复进入列表 | 按专辑 ID 去重 |
| 同名但不同语言或发行版本 | 分别保留并标明已确认差异 |
| 关联更新但页面仍展示旧数据 | 刷新相关索引与缓存，核验艺人页和专辑页一致性 |
| 关联错误 | 撤销错误关系并保留修正记录 |

### 10.3 需求二异常规则

| 异常 | 处理 |
|---|---|
| 第三方广告 SDK 超时 | 跳过展示，继续原任务 |
| 素材无关闭按钮 | 客户端拒绝展示 |
| 关闭后误触跳转 | 可拦截的误跳转立即取消并恢复原页面；已进入外部页面或应用时，在用户返回后恢复原任务，并记录异常素材与点击区域 |
| 会员状态延迟 | 以服务端最新权益为准，争议推广暂停展示 |
| 离线缓存推广过期 | 删除缓存，不展示 |
| 多个内容同时满足条件 | 必要安全、服务及权益状态优先；用户主动任务优先于普通推广，普通推广遵守统一打断预算 |
| 偏好同步失败或账号切换 | 本次关闭在本地立即生效，状态说明同步情况；账号偏好隔离 |
| A/B 实验规则冲突 | 采用干扰更低的处理规则并记录冲突 |

### 10.4 需求三异常规则

| 异常 | 处理 |
|---|---|
| 退出或屏蔽时断网 | 本地停止接触并显示同步状态，网络恢复后确认服务端结果 |
| 提交失败或受理超时 | 保留材料；超时先核对受理结果，再使用原提交标识重试 |
| 进入超时未结案状态 | 保持真实处理状态，生成延迟说明并内部升级 |
| 结案结果保存失败 | 重试并告警，避免发布缺少结论的结案状态 |
| 系统通知或设备推送失败 | 独立重试，举报记录与详情保持可查询 |
| 点击历史通知 | 展示原节点及当前最新状态，保留历史结论 |
| 重复记录或合并审核 | 关联原事项，保留各举报人的独立查询与反馈 |
| 原内容被删除 | 根据留存规则保留必要证据和原标识，说明材料可用情况 |
| 补充期限或材料保存期届满 | 事先说明截止条件，按规则反馈处理结论及后续选择 |
| 用户撤回 | 记录撤回原因和时间，必要安全处理使用独立规则 |

## 十一、非功能要求

### 11.1 性能与稳定性

- 歌手作品列表采用分页和懒加载，大列表不得阻塞返回、筛选和播放控制。
- 作品关联更新同步刷新相关索引和缓存，支持错误关系撤销。
- 推广服务或第三方 SDK 故障不得阻断播放器、搜索和个人音乐入口。
- 一起听退出和本地屏蔽优先于服务端响应完成。

### 11.2 可用性

- 关键入口在不同首页模式中保持可见、含义清楚和正常触控尺寸，布局与内容权重调整保持入口路径稳定。
- 参与身份和语言版本使用明确文字，沿用现有专辑信息层级。
- “提交中”“已受理”“处理中”“待补充”和“已结案”使用明确、不同的状态文案。
- 空状态、错误状态和部分成功状态均提供下一步操作。

### 11.3 隐私与安全

- 举报分析只记录必要的匿名标识、场景、内容标识、状态和结果代码。
- 举报材料与普通行为分析数据分区存储并控制访问权限。
- 推广埋点不采集评论内容、私信内容和举报材料。
- 屏蔽关系、案件详情和处理结果按照账号权限隔离。

### 11.4 可配置性

- 推广类型、频次、会员适用规则、匹配类别、举报类型和状态文案由服务端配置；用户主动保存的显示偏好独立维护。
- 服务异常时，客户端仍须保证素材异常不展示、普通推广不遮挡播放、退出与屏蔽先在本地生效。

## 十二、数据埋点与效果指标

### 12.1 需求一

复用艺人页、专辑页与信息纠错事件，补充参与关系来源、版本、专辑标识及纠错结果字段。

- 关联覆盖率＝已正确展示的确认关联数／核对样本中应展示的确认关联数。
- 错关联率＝抽检中错误的新增关联数／抽检新增关联数。
- 任务验证：从艺人页找到指定参与合集与目标语言版本，记录成功情况、步骤和耗时。
- 纠错验证：修正后检查艺人页、专辑页与歌曲署名的一致性。

### 12.2 需求二

#### 12.2.1 事件口径

跨页面推广事件统一携带活动标识、页面与广告位、会话标识、展示形式及账号权益状态。实际曝光按同次展示标识去重；请求和预加载不计曝光。音乐推荐与商业推广分别统计，自动播放与用户主动播放分别记录。实际实验标识缺失时记录为未知，不按首页样式推断分组。

| 事件 | 触发时机 | 关键字段 |
|---|---|---|
| promotion_request | 收到普通推广请求 | 类型、场景、权益状态 |
| promotion_decision | 展示、转换形式或放弃 | 决策原因、频次、匹配依据类别、实际实验标识 |
| promotion_impression | 素材实际进入可视区域 | 活动、页面、广告位、会话、形式、展示标识 |
| promotion_close | 关闭推广 | 展示时长、关闭区域、作用范围 |
| promotion_click | 主动打开推广 | 活动、素材、目标入口 |
| promotion_feedback | 不感兴趣或减少同类推广 | 活动、类别、反馈类型、作用范围 |
| promotion_task_resume | 关闭或返回后接续原任务 | 任务类型、原页面、恢复结果及耗时 |
| home_preference_save | 保存首页与显示偏好 | 首页模式、模块、用户主动操作类型 |
| core_task_start | 测试下达任务时，或线上用户明确发起任务时 | 任务类型、首屏模式、启动或返回时间、首屏可交互时间 |
| core_task_result | 搜索、识曲、播放或个人音乐任务到达对应节点 | 完成状态、步骤、耗时、放弃节点 |
| recommendation_action | 推荐内容曝光、自动或主动播放、收藏及反馈 | 内容类别、页面模式、动作、触发来源、实际实验标识 |

#### 12.2.2 任务与功能可达性

在预设任务测试中分别要求搜索指定歌曲、识别短时环境音乐、打开个人歌单及恢复原播放。任务在下达时登记，包含未找到入口和放弃的样本；线上未知意图的会话单独统计，不以目标入口点击作为任务分母的唯一来源。记录首次使用、熟悉使用与账号切换条件下的结果。

- 入口首击正确率＝首次操作命中目标入口的任务数／指定任务数。
- 任务完成率＝到达任务完成节点的任务数／指定任务数；未找到入口或中途放弃计入未完成。
- 启动或返回到任务完成的总耗时：包含开屏、加载、入口查找及任务操作，保留失败和放弃记录。
- 入口发现耗时与操作步骤：从首屏可交互至找到目标入口；搜索、识曲和个人音乐分别报告，与总耗时分开呈现。
- 识曲任务分别记录采集启动时间与识别结果，系统首次授权等待单列；测试使用一致音源和时间窗。
- 任务恢复率与恢复耗时：关闭推广或返回应用后，接续原播放、搜索或阅读任务的情况。
- 音频中断、音乐信息遮挡和控件受阻分别记录，音频未暂停不等同于任务未受影响。

不同账号的心动页、推荐页案例用于检验首屏结构、入口发现、模式切换和偏好恢复。比较布局效果时控制版本、权益、网络及任务条件，采用同账号界面实验或交叉顺序任务测试；账号截图差异不直接作为算法效果或因果结论。

#### 12.2.3 推广接受度与个性化效果

- 关闭后重复展示率＝活动关闭后仍发生被动曝光的会话数／关闭该活动的会话数。
- 误跳转率及立即返回情况：区分明确点击、关闭区域操作和正常持握或滑动引发的跳转。
- 不感兴趣与减少同类反馈：按实际曝光统计，观察反馈后同活动及同类展示的变化。
- 推广有效转化：按活动目标核对实际完成的操作，单列点击后立即返回和无效跳转。
- 激励广告：记录主动选择、完成、权益到账及原任务恢复，区分被动入口曝光和主动广告观看。
- 音乐推荐：自动播放的曝光与收听单列；主动播放、收藏、持续收听及负面反馈与搜索、识曲和个人音乐任务指标共同评价。

#### 12.2.4 商业与体验联合判断

会员状态采用未登录、非会员、有效且非临近到期、临近到期四个互斥分组，到期窗口由配置确定。权益暂不可确认的记录单列为未知。免费听歌模式、首页模式及任务类型独立分层记录。比较每次使用的收入或有效转化、总曝光、任务完成和负面反馈，分别验证场景控制、内容匹配及二者结合的效果。

入口保障和任务指标作为验收条件；推荐点击或广告点击的增长不能单独构成策略通过依据。指标阈值根据现状基线和任务测试确定。

### 12.3 需求三

受理成功率按用户确认提交的去重请求统计；状态可查率按每位举报人的已受理记录统计，重复提交按提交标识去重；结案结果覆盖、结案通知及结果查看按“受理记录＋结案版本”统计。每轮处理形成结论时登记应发布的版本，复核形成新版本，历史版本继续保留；发布失败仍纳入覆盖检查。后台合并审核不合并各自的反馈记录。应用内消息生成、设备推送状态和用户查看分别记录，未知送达状态单列。

| 事件 | 触发时机 | 关键字段 |
|---|---|---|
| report_submit_result | 提交失败、受理超时或确认受理 | 提交标识、场景、问题类别、结果代码 |
| report_status_change | 真实处理状态发生变化 | 记录标识、原状态、新状态、更新时间 |
| report_material_action | 请求补充或完成补充 | 材料类别、动作、截止条件 |
| report_overdue | 达到配置时限仍未结案 | 风险类别、适用时限、等待时长、升级状态 |
| report_case_closed | 形成处理结论或更新结案结果发布状态 | 处理轮次、结论类别、原因类别、版本、发布状态、结案时间 |
| report_notice_result | 应用内通知生成或设备推送返回状态 | 通知类型、记录版本、渠道、成功失败或未知 |
| report_record_open | 从通知或记录入口打开详情 | 来源、当前状态、记录版本 |
| report_result_view | 举报人查看可查询的结案结果 | 结论类别、入口来源、结果版本 |
| block_sync_result | 本地隔离或服务端屏蔽状态变化 | 场景、适用范围、网络、结果 |

- 受理成功率：成功受理的去重请求数／用户确认提交的去重请求数。
- 状态可查率：可在记录入口和详情查询的记录数／应可查询的已受理记录数。
- 结案结果覆盖率：具备完整结论、原因类别、结案时间及后续说明且前台可查的结案版本数／后台已形成结论的应发布结案版本数；未发布版本计入分母，按各结论类型分别检查。
- 处理时长：分别报告受理确认、每轮受理至结案总时长及平台处理耗时，等待用户补充时间单列；复核按新处理轮次计算。
- 未结案等待：统计全部已受理且未结案记录的等待分布，按已受理排队、处理中和待补充分层；分别报告总等待、平台处理耗时及等待用户补充时间，并检查超时和升级情况。
- 通知完整性：关键节点消息是否成功写入；结案通知按受理记录及结案版本核对，设备推送送达和未知状态另行统计。
- 结果查看率：举报人查看过的结案版本数／前台可查询的结案版本数。
- 配套保护：检查退出即时生效、屏蔽同步结果及同账号再次接触情况。

### 12.4 数据使用要求

- 作品关联补全采用样本核对与任务走查；推广和举报功能依据业务周期及有效事件量确定基线期。
- 灰度期同时观察产品指标、商业指标和安全指标。
- 需求二的任何实验不得只以广告点击率作为胜负依据。
- 需求三的“举报量下降”不能单独代表治理改善，需要结合受理成功率、处理时长、已认定违规行为的再次发生情况及用户结果查看情况。

## 十三、依赖与风险

### 13.1 需求一

| 依赖／风险 | 影响 | 处理方案 |
|---|---|---|
| 参与角色或身份信息不足 | 漏关联或误关联 | 保留来源；疑点由内容运营复核 |
| 将发行公司等同于参与艺人 | 大量无关专辑进入主页 | 按明确的作品参与关系关联 |
| 版本数据混淆 | 语言及发行版本被覆盖 | 独立保留专辑 ID 与已确认版本信息 |
| 索引或缓存更新不同步 | 不同入口显示不一致 | 关联修正同步刷新，并进行跨页面验收 |

### 13.2 需求二

| 依赖／风险 | 影响 | 处理方案 |
|---|---|---|
| 商业曝光及收入变化 | 展示规则影响变现 | 比较有效转化、每次使用收益及任务完成，按场景逐步验证 |
| 第三方素材或SDK异常 | 遮挡、误跳转及恢复失败 | 展示前校验关闭和跳转，异常素材停止展示 |
| 权益状态不同步 | 推广不适用或播放限制解释不一致 | 使用统一权益判断，异常时暂停争议推广 |
| 兴趣判断过时或信息不足 | 反复推送不相关内容 | 当前主动行为和拒绝优先，支持反馈与偏好调整 |
| 个性化弱化功能入口 | 搜索、识曲及个人音乐任务受阻 | 固定一级导航与关键入口，检查首屏识别和任务完成 |
| 仅凭点击评价策略 | 误触或内容消费增长掩盖任务损失 | 联合使用有效转化、入口发现、任务恢复和负面反馈 |
| 不同账号首屏成因不明 | 将设置、灰度等差异误归因于算法 | 记录实际配置，采用控制条件的布局测试 |

### 13.3 需求三

| 依赖／风险 | 影响 | 处理方案 |
|---|---|---|
| 审核状态与前台映射不一致 | 用户误解真实进度 | 统一状态、结论代码和实际更新时间，保留历史版本 |
| 只通知已处置结果 | 未认定违规等事项长期无后文 | 所有结案类型均生成可查询结果与通知 |
| 审核容量不足 | 未结案事项积压 | 风险分队列、时限配置、超时升级及真实延迟说明 |
| 通知失败或消息被淹没 | 用户误以为没有处理 | 关键通知跳转同一详情，集中记录可主动查询 |
| 结果保存与结案状态不同步 | 显示结束却缺少结论 | 结果与终态一致性校验，失败重试及告警 |
| 合并处理遗漏个人反馈 | 部分举报人无法跟进 | 各举报人保留独立记录与结果关联 |
| 披露过多或举报滥用 | 隐私和正常表达受损 | 限定可公开结论，依据证据处理，保留复核及个人控制 |

### 13.4 团队依赖

| 团队 | 主要责任 |
|---|---|
| 客户端 | 页面、状态、缓存、任务恢复及本地退出与隔离 |
| 内容平台 | 歌手作品关系、内容类型和可播放状态 |
| 商业化 | 推广类型、素材、频次和商业指标 |
| 会员系统 | 权益判断与推广减免 |
| 社区安全 | 举报分类、审核规则、状态和处理结果 |
| 客服与运营 | 用户反馈、内容纠错、案件补充和异常处理 |
| 数据 | 事件口径、基线、灰度看板和异常监控 |
| 法务与隐私 | 广告展示、举报材料、结果披露和保存期限 |

## 十四、验收标准

### 14.1 需求一

| 编号 | 验收条件 |
|---|---|
| 1.1 | 专辑、歌曲、参与者与发行公司按真实角色展示，关联依据可追溯 |
| 1.2 | BOI 案例中的日文合集可从艺人现有作品列表到达，合集原署名保留；部分参与案例仅说明实际参与范围 |
| 1.3 | 同一专辑在列表中去重，日文与英文等不同版本分别可达，语言信息与发行资料一致 |
| 1.4 | 通过现有入口完成关联纠错后，艺人页、专辑页及歌曲署名一致；错误关系可撤销 |

### 14.2 需求二

| 编号 | 验收条件 |
|---|---|
| 2.1 | 商业广告、功能引导、激励入口与必要权益状态可区分；自动展开的阻断式引导纳入打断预算，非阻断轻提示按曝光及密度控制 |
| 2.2 | 同活动关闭记录跨页面生效，需确认、关闭或等待的推广共享打断总量；固定卡片满足独立曝光与密度规则，返回时不集中补弹 |
| 2.3 | 被动推广不覆盖或替换音乐信息和操作区；主动推广按用户选择进入和返回，恢复时校验权益与最新播放状态，阅读位置稳定 |
| 2.4 | 关闭与跳转热区分离；刷新和普通浏览保持原功能，正常摇动不触发通用广告落地页 |
| 2.5 | 首页落点和可选模块由用户主动调整，按账号保存、恢复；推荐调整不覆盖用户设置 |
| 2.6 | 受限歌曲与免费时长分别解释并合并重复提示；激励条件、到账和返回路径清楚，已享有权益不重复推销 |
| 2.7 | 正式版本核验覆盖账号、首页模式与核心任务；实际曝光、遮挡和恢复情况留有记录 |
| 2.8 | 推广先通过权益、场景、关闭与频次校验，再按主动行为、兴趣和反馈匹配；排序不豁免展示限制 |
| 2.9 | 各首页模式保留位置稳定、首屏可发现的搜索、识曲和个人音乐入口；无自动折叠、弱化或增加层级，完成首次使用与账号切换任务测试 |
| 2.10 | 关闭按会话、不感兴趣按活动周期、减少同类按类别分别生效；更换素材不能重置反馈，账号偏好隔离且可恢复 |

### 14.3 需求三

| 编号 | 验收条件 |
|---|---|
| 3.1 | 评论、私信及陌生互动可就近提交；离开原场景后仍可找到已受理记录 |
| 3.2 | 疑似违规、内容质量及个人偏好按对应流程处理，必要材料要求明确 |
| 3.3 | 服务端确认后显示已受理；失败保留草稿，超时重试不重复生成记录 |
| 3.4 | 已受理、处理中、待补充和已结案可查询，更新时间对应实际事件，补充要求和截止条件清楚 |
| 3.5 | 全部结案类型均有结论、原因及后续说明，未认定违规和材料不足同样反馈；结案状态与结果一致 |
| 3.6 | 退出不依赖举报完成，网络异常先停止本机接触，屏蔽范围和同步状态清楚 |
| 3.7 | 系统通知与记录进入同一详情，历史节点和最新状态可辨认；推送失败或关闭时结果仍可查 |
| 3.8 | 超过配置时限的未结案记录触发延迟说明和内部升级，最终结案继续反馈结果 |
| 3.9 | 重复提交关联原记录，合并审核仍覆盖各举报人的反馈；举报量不直接替代违规认定 |

## 十五、上线与验证计划

### 15.1 阶段一：现状基线

- 使用当前正式版本完成三项需求的现网复测。
- 需求一核对参与关系、版本及跨页面展示；需求二、三按确定的观察周期采集基础指标，确认推广类型、举报状态和技术接口。

### 15.2 阶段二：小范围灰度

- 需求一先修正已确认的漏关联记录，核验展示后，将关系核对纳入后续入库及纠错流程。
- 需求二先验证任务与入口保护、跨页面频控和防误触，再验证内容匹配、反馈及用户显示偏好。
- 需求三首期同时连通受理、可查进度、必要补充、全类型结案反馈和通知关联，并配置超时处理；退出与屏蔽复用现有能力。
- 每项需求均配置回退开关。举报功能回退时，保留已受理记录及其查询、处理和结果反馈链路，存量事项继续跟进至结案。

### 15.3 阶段三：效果评估

- 需求一观察关联覆盖、错关联、指定合集查找与跨页面信息一致性。
- 需求二同时观察入口发现、识曲启动、任务完成、有效转化、反馈及任务恢复。
- 需求三同时观察受理成功、进度可查、各结案类型的结果覆盖、未结案等待、通知完整性及配套保护。
- 灰度期间出现安全、数据一致性或大规模任务失败时，停止扩量并回退受影响功能。
